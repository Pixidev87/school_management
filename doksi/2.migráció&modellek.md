School Management App – Adatbázis és Model réteg dokumentáció
Áttekintés
A projekt backend alapját egy MySQL adatbázis adja, amelyet Laravel Eloquent ORM segítségével kezelünk. Az adatbázis 21 táblából áll, amelyek az iskola összes főbb funkcióját lefedik.

Miért Laravel Eloquent?
Az Eloquent egy ORM (Object-Relational Mapper) – ez azt jelenti, hogy az adatbázis táblákat PHP osztályokként (modellekként) kezeljük, és nem kell nyers SQL lekérdezéseket írni. Például:

// Nyers SQL helyett:
SELECT * FROM students WHERE id = 1;

// Eloquent-tel:
Student::find(1);

Migrációk

A migráció egy verziókezelt adatbázis séma – olyan mint egy Git commit, de az adatbázis szerkezetének. Minden tábla létrehozása, módosítása egy-egy migrációs fájlban van rögzítve, így a csapat minden tagja ugyanazt az adatbázis struktúrát tudja felépíteni egyetlen paranccsal:

sail artisan migrate

Táblastruktúra és magyarázatok

1. users
Laravel alapértelmezett tábla. Az adminisztrátorok és felhasználók bejelentkezési adatait tárolja. Kapcsolódik az értesítésekhez.

2. teachers
A tanárok adatait tárolja. Nincs foreign key függősége, ezért ez az egyik első tábla amit migrálunk.

Mező                Típus                   Magyarázat

name                string                  Tanár neve
email               string,uniqueEgyedi     email cím
phone               string,nullable         Telefonszám
qualification       string,nullable         Végzettség
date_of_birthdate,  nullable                Születési dátum
gender              enum                    male/female/other
address             string,nullable         Lakcím
joining_date        date,nullable           Belépés dátuma

3. classes
Az osztályokat tárolja. Hivatkozik a teachers táblára (osztályfőnök).

Mező                Típus                   Magyarázat

name                string                  Osztály neve (pl. "10A")
section             string,nullable         Szekció
room_number         string,nullable         Terem száma
class_teacher_id    foreignId,nullable      Osztályfőnök (teachers)

Miért set null az onDelete? Ha egy tanárt törölnek, az osztály nem tűnhet el – csak ideiglenesen osztályfőnök nélkül marad.

4. students
A diákok adatait tárolja. Hivatkozik a classes táblára.

Mező                Típus                   Magyarázat
name                string                  Diák neve
email               string,unique           Egyedi email
phone               string,nullable         Telefonszám
address             text,nullable           Lakcím

gender              enum                    male/female/other
roll_number         string,unique           Egyedi azonosító
class_id            foreignId               Melyik osztályba jár

Miért softDeletes? A diák törléskor nem törlődik fizikailag az adatbázisból – csak kap egy deleted_at időbélyeget. Az adatok megmaradnak, visszaállítható.

6. parents (Guardian modell)
A szülők/gondviselők adatait tárolja. Hivatkozik a students táblára.

Mező                Típus                   Magyarázat
guardian_name       string                  Gondviselő neve

address             text,nullable           Lakcím

Miért Guardian a modell neve? A Parent foglalt PHP kulcsszó, ezért átneveztük Guardian-ra. A tábla neve marad parents.
Miért cascade az onDelete? Ha egy diákot törölnek, a hozzá tartozó szülői adatoknak sincs értelme megmaradni.

Model réteg
Minden táblához tartozik egy Eloquent Model osztály. A modellek feladata:

$fillable – meghatározza melyik mezők tölthetők ki tömegesen (mass assignment védelem)
$casts – automatikus típuskonverzió (pl. date string → Carbon objektum)
Kapcsolatok – meghatározza hogyan kapcsolódnak egymáshoz a táblák

Kapcsolatok típusai a projektben
Student     → belongsTo  → SchoolClass      (egy diák egy osztályba jár)
Student     → hasMany    → Guardian         (egy diáknak több gondviselője lehet)
Student     → hasMany    → Attendance       (egy diáknak több jelenléti bejegyzése van)
Student     → hasMany    → ExamResult       (egy diáknak több vizsgaeredménye van)
Student     → hasMany    → Fee              (egy diáknak több díja lehet)

Teacher     → hasMany    → Subject          (egy tanár több tantárgyat taníthat)
Teacher     → hasMany    → SchoolClass      (egy tanár több osztály osztályfőnöke lehet)

SchoolClass → belongsTo  → Teacher          (egy osztálynak egy osztályfőnöke van)
SchoolClass → hasMany    → Student          (egy osztályban több diák van)

Exam        → hasMany    → ExamResult       (egy vizsgán több diák írhat)
ExamResult  → belongsTo  → Exam            (egy eredmény egy vizsgához tartozik)
ExamResult  → belongsTo  → Student         (egy eredmény egy diákhoz tartozik)

Transport   → hasMany    → TransportStop    (egy járatnak több megállója van)
Transport   → hasMany    → TransportStudent (egy járatot több diák használ)

Notification → hasMany   → NotificationRead (egy értesítést többen olvashatnak)

SoftDeletes használata
A következő modelleknél van bekapcsolva a soft delete:

Student, Teacher, SchoolClass, Subject, Guardian
Exam, Fee, LibraryBook, Transport, Notification

Ezeknél a törlés nem fizikai – a rekord megmarad az adatbázisban, csak kap egy deleted_at értéket. Visszaállítható a restore() metódussal.
